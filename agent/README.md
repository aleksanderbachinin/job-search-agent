# jobagent: отбор вакансий Hirify с карточками в Telegram

Сервис принимает новые вакансии из сохранённых фильтров Hirify, отсеивает неподходящие и присылает остальные в Telegram-бот. Под каждой карточкой есть кнопки решения, а `/stats` показывает воронку.

Всё, что нужно агенту, лежит в папке «Agent Job Search»: код в `agent/`, а рядом файлы, на которые опирается оценка и генерация (критерии, резюме, гайд по письмам, примеры откликов). Остальная папка `job-search` сервису не нужна. Команды ниже выполняются из «Agent Job Search».

Логика работы целиком, без технических деталей запуска: [HOW_IT_WORKS.md](../HOW_IT_WORKS.md).

```
Hirify вебхук ─┐
               ├─► очередь (SQLite) ─► правила ─► Haiku по карточке ─► полный текст ─► Haiku по тексту ─► Sonnet ─► бот
опрос фильтров ┘
```

## Что делает каждая ступень

1. **Правила** (`rules.py`, бесплатно). Отсекают:
   - уже отправленные отклики;
   - junior-грейды;
   - роли не по профилю по названию: дизайнер, аналитик, разработчик, продажи и т.п.
2. **Haiku по карточке** (`scoring.py`, доли цента). Отсеивает явные несовпадения по роли и направлению. При сомнении пропускает вакансию дальше. Полную вакансию эта ступень не открывает, лимит открытий на Hirify не тратится.
3. **Полный текст** (`vacancies.read`, одно открытие из дневного лимита). Вакансии старше `MAX_AGE_DAYS` отсеиваются.
4. **Haiku по тексту** (`scoring.py`, около 0,02 цента). Отсеивает явные стоп-факторы из текста: офис или гибрид без релокации, нельзя из России без переезда, junior, не продуктовая роль. Идёт до LinkedIn-проверки, поэтому отсеянная вакансия не тратит кредиты ScrapeCreators. При сомнении пропускает. `PREFILTER=0` выключает.
5. **Sonnet.** Ставит оценку 1–5 по [search_criteria.md](../search_criteria.md) и [файлу опыта](../experience/Bachinin_Alexander_Experience.md), сверяется с примерами из [applied_examples.md](../applied_examples.md). Добавляет RU-метку по тексту вакансии и вывод: два довода «за», один «против», пробелы. С оценкой от `MIN_SCORE` (по умолчанию 4) вакансия уходит в бот.

Каждый шаг пишется в таблицу `events`: из неё строится `/stats`, там же токены LLM по каждой вакансии, включая чтение и запись кеша. System prompt Haiku по тексту и Sonnet кешируется на час.

## Кнопки в боте

- **✅ Откликнулся** записывает отклик в трекер Hirify (`applications.track`). После этого появляются кнопки этапов: интервью, оффер, отказ. Они тоже уходят в трекер.
- **⏭ Пропустить** спрашивает причину и скрывает вакансию в Hirify. С причиной «Компания неинтересна» скрываются все вакансии компании. Причины видны в `/stats`.
- **📝 Подготовить отклик** собирает пакет отклика: PDF-резюме на одну страницу и сопроводительное письмо под вакансию, ответом на карточку. Кнопка есть только у новых карточек и только если заданы `CANDIDATE_EMAIL` и `CANDIDATE_LINKEDIN` (раздел «Пакет отклика»).
- **✏️ Переделать** под пакетом: бот спрашивает, что поправить, и пересобирает пакет с вашей правкой.
- **/stats**: воронка за 7 дней и за всё время, строка о пакетах (сколько собрано, переделок, средняя стоимость). **/stats 30**: за 30 дней.

Бот отвечает только владельцу (`TELEGRAM_OWNER_ID`). Без вашего нажатия сервис ничего не отправляет работодателям и не раскрывает контакты.

## Запуск

### 1. Ключи

| Переменная | Где взять |
|---|---|
| `HIRIFY_API_KEY` | hirify.me/mcp-api → API → создать ключ |
| `TELEGRAM_BOT_TOKEN` | @BotFather → `/newbot` |
| `TELEGRAM_OWNER_ID` | ваш числовой id, например через @userinfobot |
| `ANTHROPIC_API_KEY` | console.anthropic.com |
| `CANDIDATE_EMAIL`, `CANDIDATE_LINKEDIN` | Контакты в шапке резюме и подписи письма. Без них пакеты отклика выключены: кнопки нет, в журнале одно предупреждение при старте |
| `CANDIDATE_TELEGRAM` | Ссылка на Telegram для тех же мест, необязательно |

Необязательные настройки пакета отклика: `PACKAGE_MODEL` (генерация резюме и письма, по умолчанию `claude-opus-5-5`), `PACKAGE_CHECK_MODEL` (проверка смысла утверждений, `claude-haiku-5-5`), `PACKAGES_DIR` (папка пакетов, по умолчанию `packages` рядом с базой `DB_PATH`). Карту требований строит `SCORING_MODEL`.

```bash
cp agent/.env.example agent/.env
```

Заполните `agent/.env`, затем напишите своему боту `/start`, иначе он не сможет вам писать.

### 2. Проверка оценки на одной вакансии

Ничего не пишет в базу и бот:

```bash
cd agent && uv run python -m jobagent.cli dry-run 1071419
```

### 3. Сервер

Нужен постоянно работающий хост с публичным HTTPS. Локальный запуск:

```bash
cd agent && uv run python -m jobagent.main
```

На сервере сервис работает под systemd, HTTPS перед портом 8080 даёт Caddy (см. «Рабочий сервер»).

### 4. Вебхук Hirify

Подключите вебхук к фильтрам. Команда создаёт эндпоинт и один раз печатает секрет подписи. Секрет впишите в `HIRIFY_WEBHOOK_SECRET` и перезапустите сервис.

```bash
cd agent && uv run python -m jobagent.cli setup-webhook https://<ваш-домен>/hirify/webhook
```

Проверка доставки:

```bash
cd agent && uv run python -m jobagent.cli test-webhook <webhook_id>
```

## Как устроен приём

- **Первый запуск.** Первые `RECONCILE_PAGES` страниц каждого фильтра помечаются как «уже было» (`baseline`) и не оцениваются. Иначе сервис потратил бы сотни открытий и LLM-вызовов на старые вакансии.
- **Вебхук.** Подпись HMAC-SHA256 проверяется до разбора тела. Повторы доставки отбрасываются по `X-Hirify-Delivery`. Одна вакансия из нескольких фильтров обрабатывается один раз.
- **Страховка.** Раз в `RECONCILE_HOURS` сервис перечитывает первые страницы фильтров и добирает пропущенное, например если сервер лежал. Весь фильтр не листается: Hirify считает массовое листание без открытий копированием каталога.
- **Сбои Hirify.** Из Таллина `api.hirify.me` попадает на сервер Hirify, который часто отвечает 503. Клиент повторяет запросы (2, 5, 15 с). Воркер при 5xx ждёт 2 минуты и не считает это ошибкой вакансии. Первичная разметка идёт в фоне и повторяется, пока не пройдёт.
- **Лимиты.** На 429 от Hirify воркер ждёт `retry_after`. При долгом простое присылает алерт в бот. Вакансию, которая трижды упала с ошибкой, бот присылает алертом.

## Проверка промптов

`eval` прогоняет шаг отсева или оценки по снимку рабочей базы и сверяет ответы с тем, что уже известно о вакансиях: оценкой Sonnet и решением Александра (откликнулся или пропустил с причиной). Рабочую базу и бот команда не трогает.

### Снимок базы

Консистентная копия через `sqlite3` backup, база на сервере открывается только на чтение. Команда из папки `agent/`:

```bash
ssh root@193.42.112.144 '/opt/jobagent/app/agent/.venv/bin/python -c "import sqlite3; s = sqlite3.connect(\"file:/opt/jobagent/data/jobagent.sqlite3?mode=ro\", uri=True); d = sqlite3.connect(\"/tmp/jobagent-eval.sqlite3\"); s.backup(d); d.close()"' && scp root@193.42.112.144:/tmp/jobagent-eval.sqlite3 data/eval.sqlite3 && ssh root@193.42.112.144 rm /tmp/jobagent-eval.sqlite3
```

Снимок лежит в `agent/data/eval.sqlite3`, результаты прогонов в `agent/data/evals/`. Папка `data/` в git не попадает. Другой снимок можно передать через `--db`.

### Команды

```bash
cd agent && uv run python -m jobagent.cli eval prefilter
cd agent && uv run python -m jobagent.cli eval prefilter --limit 20
cd agent && uv run python -m jobagent.cli eval triage
cd agent && uv run python -m jobagent.cli eval scoring --limit 10
cd agent && uv run python -m jobagent.cli eval prefilter --compare data/evals/<было>.json
cd agent && uv run python -m jobagent.cli eval prefilter --compare data/evals/<было>.json data/evals/<стало>.json
```

- **prefilter** берёт вакансии с сохранённым полным текстом, которые проходят правила (украинские, например, отсекаются ещё до Haiku). Свежесть не проверяется: в снимке почти все вакансии уже старые. Около минуты и пары центов на весь снимок.
- **triage** берёт карточки всех вакансий, кроме `baseline` и отсеянных правилами.
- `--limit N` для prefilter и triage берёт выборку вместо всего снимка: по одной вакансии из каждой корзины по кругу (отклики, 4–5, 3, 1–2, без метки), так что вакансии, по которым считаются ложные отсевы, попадают первыми. Без `--limit` идёт весь снимок: около 320 вакансий для prefilter и 400 для triage. С `--compare` к прогону с `--limit` проверяются те же вакансии, что в нём.
- **scoring** заново оценивает вакансии Sonnet. `--limit` обязателен, не больше 30: около 2 центов за вакансию. Вакансии берутся по одной на каждую старую оценку сверху вниз, отклики первыми. С `--compare` оцениваются те же вакансии, что в прошлом прогоне.
- `--compare <было.json>` прогоняет шаг заново и сравнивает с прошлым прогоном. С двумя файлами команда только сравнивает их, модель не вызывается.
- Запросы идут по 4 одновременно (`--concurrency`). Вакансия, на которой модель так и не ответила, в подсчёт не входит и печатается в «Ошибки модели».

### Подписка или ключ API

По умолчанию `eval` вызывает модели через Claude Code (`claude -p`), то есть по подписке Claude, а не за счёт `ANTHROPIC_API_KEY`. Ключ из `.env` в `claude -p` не передаётся. Перед первым прогоном войдите в Claude Code по подписке:

```bash
claude auth login
```

- Каждый запрос — отдельный процесс `claude -p` с тем же system prompt и той же JSON-схемой, что в сервисе, без инструментов, настроек и MCP. Кешем промпта управляет Claude Code, поэтому строка «Токены» в отчёте отличается от прогона через API.
- Лимиты общие с работой в Claude Code. Полный цикл triage + prefilter + scoring — около 760 запросов. Если лимит подписки или вход кончились посреди прогона, остальные вакансии не запускаются, а отчёт заканчивается строкой «⚠ Прогон неполный». Такой прогон как базу для `--compare` не берите.
- Если в аккаунте Claude включён Extra usage, после лимита подписки запросы продолжатся, но за деньги.
- `--backend api` прогоняет через Claude API за счёт ключа, как работает сервис на сервере. Нужен, когда важно совпадение с продакшеном (кеш, fallbacks). Стоимость: triage и prefilter по снимку — около 10 центов каждый, scoring — около 1,3 цента за вакансию.
- Бэкенд записан в файле прогона и в заголовке отчёта. Сравнивайте прогоны одного бэкенда.
- Свои скрипты с моделями (повторы, другие критерии) создают клиент так же: `Scorer(..., client=ClaudeCodeClient())` из `jobagent.claude_code`. `anthropic.AsyncAnthropic()` в них берёт ключ из `.env` и тратит кредиты API.

### Как читать отчёт

Для prefilter и triage выводится таблица по корзинам: сколько вакансий в корзине и сколько шаг отсеял.

| Корзина | Что в ней |
|---|---|
| откликнулся | Александр откликнулся. Корзина важнее оценки |
| оценка 4–5 | Sonnet поставил 4 или 5. Сюда же попадают пропущенные Александром, причина видна в списке |
| оценка 3, оценка 1–2 | Отсев здесь — экономия, а не ошибка |
| без метки | Sonnet вакансию не оценивал: её отсеяли раньше или она устарела |

**Ложный отсев** — вакансия из корзин «откликнулся» и «оценка 4–5», которую шаг отсеял. Каждая печатается с причиной модели. Главная метрика: ложных отсевов 0. Если правка промпта отсеивает больше в «оценке 1–2», но даёт хоть один новый ложный отсев, она хуже.

У triage корзины с метками почти всегда пустые по отсеву: туда попали только вакансии, которые triage уже пропустил в работе. Новые ложные отсевы там значат, что правка ужесточила шаг.

Для scoring выводится матрица «старая оценка → новая», средняя разница (новая минус старая), сколько оценок совпало и сколько вакансий пересекли порог `MIN_SCORE` в любую сторону: они меняют то, что приходит в бот.

В JSON по каждой вакансии лежат метка, корзина и ответ модели целиком, а также хеш текста system prompt (`prompt_hash`), коммит (`git_sha`, с `-dirty` при незакоммиченных правках) и токены.

### Правило для правки промпта

1. До правки: `eval <шаг>` на текущем промпте. Это «было».
2. Правка промпта.
3. После правки: `eval <шаг> --compare data/evals/<было>.json`.
4. В «Изменились» разобрать каждую вакансию. В сводке «до → после» ложных отсевов не больше, чем было, в идеале 0.
5. Коммит правки, в сообщении цифры до и после.

Модель отвечает по-разному даже на тот же промпт. Два прогона prefilter подряд без правки разошлись на 6 вакансиях из 118, все с оценкой 1–2. Значит, 5–6 изменений в корзинах с низкой оценкой — шум. Ложный отсев в корзинах «откликнулся» и «оценка 4–5» разбирается всегда. Сравнивается только вердикт: другая формулировка причины изменением не считается.

## Пакет отклика

По кнопке «📝 Подготовить отклик» сервис в фоне собирает пакет, одна сборка за раз:

1. карта требований: требование вакансии → номера фактов из файла опыта или «пробел» (`SCORING_MODEL`);
2. резюме и письмо со ссылками на факты (`PACKAGE_MODEL`);
3. проверка кодом (числа, названия, состав мест работы, тире, стоп-фразы, 300 слов, язык каждого утверждения и всего документа; тема и финал письма без чисел и названий, кроме компании и роли) и проверка смысла (`PACKAGE_CHECK_MODEL`: усиление, маскировка пробелов карты, утверждения об опыте без номеров);
4. одна пересборка резюме или письма, если в нём есть нарушение класса remove или fail, а в письме ещё тире или стоп-фраза (длина, число пунктов и нет компании или роли в письме — только предупреждение); что не прошло и после неё, удаляется и попадает в сводку «убрал: <место> (<код>: <подробности>)»;
5. PDF ровно на одну страницу: если не влезает, сокращается содержание, а не шрифт. Порядок — `CUT_ORDER` в `package_rules.py`: пункты и места работы, затем хвост навыков и summary до минимума.

Пока идёт сборка, ответом на карточку висит статус: одно сообщение, которое бот правит на каждом шаге (✓ сделан, ▸ идёт, · впереди) и в конце заменяет итогом: «✅ готов», «❌ не собрался: <код>» с отметкой шага, на котором упало, «⚠️ собран, но не отправлен» или «⛔ прервана перезапуском сервиса». Шаг пересборки появляется, только если она была; у правки нет карты требований, она берётся из прошлой версии. Сбой Telegram при отправке или правке статуса сборку не останавливает. Если сервис упал без штатной остановки, статус остаётся «⏳», а в базе версия при следующем старте станет `failed` (`restart`).

Ошибка разметки файла опыта (пункт без номера `[КОД-N]`, повтор номера) выключает только пакеты: кнопки нет, отбор вакансий работает, в журнале при старте предупреждение с классом ошибки, без текста файла. Место ошибки покажет `cli package`: там ошибка печатается целиком.

Каждая версия лежит в `PACKAGES_DIR/<slug>/v<N>/` с правами только для сервиса: PDF, `resume.md`, `letter.md`, `experience_map.md`, JSON и `check.json` с тем, что убрано. В события и журнал попадают только коды и числа, без текстов. Сборка, оборванная перезапуском, при следующем старте помечается `failed` с кодом `restart`.

### Команды

Обе требуют `CANDIDATE_EMAIL` и `CANDIDATE_LINKEDIN` и ничего не пишут в базу и бот.

```bash
cd agent && uv run python -m jobagent.cli package 1279450
cd agent && uv run python -m jobagent.cli package 0 --file tests/fixtures/packages/qic_1265514.json --out data/packages-cli/qic
cd agent && uv run python -m jobagent.cli package-eval
```

- **package** собирает пакет одной вакансии: из Hirify по id или из JSON полного текста (`--file`, как у `dry-run`). Файлы кладёт в `--out`, по умолчанию `agent/data/packages-cli/<slug>/`, в консоль печатает сводку проверки, число вызовов и стоимость. Это для приёмки и отладки.
- **package-eval** собирает пакеты по всем фикстурам `tests/fixtures/packages/` (другая папка: `--fixtures`). Тратит Opus, около доллара на прогон: запускать с согласия Александра. Отчёт печатается и сохраняется в `agent/data/evals/<время>-package.json`, рядом с отчётами `eval`.

Фикстуры: полный текст вакансий ручных пакетов из Hirify без контактов (AI Product Builder `1279450`, QIC `1265514`, Intch `1084401`) и ловушки, написанные вручную: инъекция в тексте вакансии, русский текст у компании с английским названием, CPO, builder с «Strong Python», скрытая компания.

### Как читать отчёт package-eval

Отчёт начинается с главного: `Убрано: N (number 3, semantic 2…)` — сколько утверждений убрано по каким кодам за весь прогон, и `Не собрано: M (composition 1, language 1…)` — какие пакеты не собрались и с каким кодом (`composition`, `language`, `no_answer`, `api_error:…`). Дальше по каждой вакансии: язык и тип, убранное по кодам, число предупреждений, была ли пересборка, шаги подгонки под страницу, страницы, слова письма, стоимость. В отчёте нет текста вакансии, резюме и письма: их смотрят через `cli package`.

Контроль в конце, всё должно быть 0:
- `повторная проверка кодом: 0 нарушений (контроль)` — те же проверки кодом на готовом пакете. Это контроль удаления, а не мера выдумок: то, что код пропустил при сборке, он пропустит и здесь. Выдумки видны по строке «Убрано» и при чтении пакетов через `cli package`;
- `тире: 0` — в тексте письма, тема включительно;
- `страниц > 1: 0`.
